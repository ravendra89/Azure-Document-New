# But team your question might be, why do we use Azure NAT Gateway?

So team, We use Azure NAT Gateway to provide outbound Internet connectivity for resources in an Azure virtual network without requiring public IP addresses on each resource.

Suppose we have a VM deployed in a private subnet. These VMs don't have public IP addresses because we don't want anyone on the internet connecting directly to them.

But these VMs still need internet access—for example, to download Windows updates, install software packages, or call external APIs.

That's exactly where Azure NAT Gateway comes in.

By Using Azure NAT Gateway, the VM can initiate outbound communication to the Internet, but external traffic cannot initiate communication with the VM.

# Lets understand Working of Azure NAT Gateway in the given diagram:

Suppose this is Virtual Network.

And Inside this VNet, there are two VMs Deployed in the private subnets without public IP address.

Both subnets are connected to a single Azure NAT Gateway.

Think of the NAT Gateway as the internet exit door for all private resources.

Instead of every VM having its own public IP, all outbound traffic is sent through this single NAT Gateway.

Now suppose this VM wants to download software updates.

The VM sends a request to the internet.

Since the VM doesn't have a public IP, the NAT Gateway replaces the VM's private IP with its own public IP address.

This process is called Network Address Translation, or NAT.

So, The internet only sees the NAT Gateway's public IP address, not the VM's private IP.

When the internet sends the response back, it arrives at the NAT Gateway.

The NAT Gateway keeps track of every outbound connection.

It knows exactly which VM initiated the request, so it forwards the response back to the correct virtual machine.

# But what happens if someone on the internet tries to directly connect to one of these virtual machines?

The answer is—they can't connect to the VM.

Azure NAT Gateway does not allow unsolicited inbound connections.

Since the VMs don't have public IP addresses, and NAT Gateway only supports outbound translation, incoming traffic is automatically blocked.

So you can see here in the diagram:

✅ VM can initiate communication to the internet.

✅ Internet can send back responses.

❌ But, Internet cannot start a new connection to the VM.

Azure Bastion establishes the remote session to the virtual machine.

For Windows Server→ by using RDP (3389)

And for Linux Server→ by using SSH (22)

This traffic remains inside the Azure Virtual Network.

####
Team, by using Azure Bastion, we can securely access virtual machines within the same Virtual Network (VNet) without opening RDP (3389) or SSH (22) ports in the VM's NSG.

The reason is that Azure Bastion and the VM are part of the same Virtual Network (VNet). When you connect through Azure Bastion, the RDP or SSH session is established from within the VNet, not from the public Internet.

Azure Bastion is deployed in the AzureBastionSubnet, it can communicate with any subnet within the same VNet. Azure automatically routes traffic between subnets, allowing Bastion to establish RDP or SSH connections to VMs anywhere in the virtual network.

Team, I'll explain the default NSG rules after we deploy the virtual machine

# Note: I'll explain the following at the VM's NSG level after the VM is created.

By default, every Azure NSG contains the following rule:

Priority	Rule	Action
65000	AllowVNetInBound	Allow

This default rule allows communication between resources within the same Virtual Network. Since both Azure Bastion and the VM are in the same VNet, the traffic is allowed automatically unless you create a custom NSG or firewall rule to block it.

As you can see,  SSH (22) port 22 is not exposed to the Internet.


####

step 4:
And this is the NSG associated with the subnet that protects VM-1.

By using an NSG, we can:

Allow RDP/SSH traffic only from Azure Bastion and prevent direct access from the Internet.

Restrict application ports such as HTTP (80) and HTTPS (443), and allow access only from trusted sources.

Control inbound and outbound traffic and prevent unwanted network communication.

Team, important point is that if there is no NSG attached to the VM , Azure uses its default network security behavior.

By default, Azure allows communication between resources inside the same Virtual Network (VNet) through the default NSG rules.

Step 5:

Now suppose the Virtual Machine needs to:

Download Windows Updates
Install packages
Download software
Connect to APIs
Access Azure Storage

The VM sends outbound traffic.

So for this, we will deploy NAT Gateway so that the traffic is routed to the NAT Gateway.

The NAT Gateway replaces the VM's private IP with its own Public IP.
This process is called Source Network Address Translation (SNAT).

The virtual machine keeps its private IP address.
Before the traffic reaches the Internet, the NAT Gateway translates the source IP (and in this case, source ip is VM private Ip) to its public IP. External services only see the NAT Gateway's public IP.

Azure NAT Gateway is used only for outbound Internet connectivity.

It allows private resources inside a Virtual Network to securely access the Internet.


One of the biggest advantages is that we don't need to assign Public IP addresses to individual Virtual Machines.

All outbound traffic leaves through a single static Public IP attached to the NAT Gateway.

Since the Virtual Machines don't have Public IPs, nobody on the Internet can directly access them.

Only outbound connections initiated by the VM are allowed.

This follows security best practices.
